# Vuxo 0.0.1

## Obiettivo

Prima versione giocabile: autenticazione, creazione personaggio, ingresso nel mondo, movimento e presenza degli altri giocatori.

## Foundation

- repository e struttura DDD iniziale;
- modello attributi personaggio e test parametrizzati;
- PostgreSQL/EF Core e Redis predisposti;
- audit di dominio per eventi e contenuti personali predisposto;
- frontend React + Phaser con shell MUI responsive;
- tema system/light/dark persistito;
- i18n predisposto con italiano e inglese e regola di contenuto narrativo canonico indipendente dalla lingua;
- runtime Ollama containerizzato predisposto per CPU e GPU opzionale;
- `ILanguageModelGateway` e adapter OpenAI-compatible separati dal dominio;
- smoke amministrativo di tool calling con test xUnit;
- profilo Ollama low-resource con un solo modello e parallelismo minimo;
- SignalR, Docker e CI/CD tracciati nel backlog 0.0.1.

## Domini production

- frontend canonico: `https://vuxo.quest` tramite GitHub Pages custom domain;
- API canonica: `https://api.vuxoapi.xyz` tramite Cloudflare Tunnel;
- build GitHub Pages predisposto con base path `/` per il dominio custom;
- deploy backend predisposto con `https://vuxo.quest` come origin CORS production predefinita.

## Engineering e coding agent

- aggiunto `AGENTS.md` come guida canonica del repository;
- aggiunti entrypoint per GitHub Copilot, Claude e Gemini che convergono sulle stesse regole;
- aggiunte istruzioni Copilot specifiche per frontend, backend e test;
- aggiunte skill riutilizzabili per feature verticali, UI/design system, i18n, testing, release/versioning e LLM/tool calling;
- documentato l'ordine con cui un agent deve recuperare contesto da codice, test, docs e issue;
- aggiunto quality gate CI che verifica coerenza tra `VERSION`, versione frontend e patch note della versione corrente.

## Quality rules

- ogni nuova UI deve riusare MUI/design token, funzionare in tema chiaro/scuro e considerare layout mobile;
- ogni stringa user-facing deve passare da i18n con almeno italiano e inglese;
- ogni regola deterministica deve essere testata, preferibilmente con test parametrizzati;
- ogni nuova versione deve includere bump versione, metadata coerenti, patch note e test verdi.
