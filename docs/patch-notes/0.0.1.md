## Osservabilità tecnica

- introdotta una pipeline OpenTelemetry distinta dall'audit di dominio: trace, metriche e log tecnici non diventano eventi funzionali e l'event store non viene usato come sistema di monitoring;
- il backend usa OpenTelemetry .NET `1.18.0` per ASP.NET Core, chiamate HTTP in uscita, runtime e OTLP; PostgreSQL usa `Npgsql.OpenTelemetry 10.0.3` e il meter nativo `Npgsql` per command/connection telemetry;
- ogni richiesta riceve `X-Correlation-ID`: un valore in ingresso viene mantenuto solo se supera la validazione, altrimenti viene derivato dal trace corrente; il player autenticato arricchisce activity e logging scope senza affidarsi a dati inviati dal client;
- il world host espone activity `world.join`/`world.leave` e metriche dedicate a durata tick, player modificati, player online, failure tick e input movimento rifiutati;
- il sampling delle trace è configurabile con `Observability:SamplingRatio`; senza `Observability:OtlpEndpoint` il gioco continua a funzionare normalmente e non tenta connessioni verso un collector;
- la telemetria PostgreSQL mantiene tempi, correlazione e metadata operativi, ma il collector production rimuove `db.query.text`, `db.statement` e `db.connection_string` prima dell'export;
- le query HTTP aggiunte come tag custom vengono prima sanificate lato applicazione: parametri come `access_token`, authorization, password, secret, API key e JWT vengono sostituiti con `[REDACTED]`;
- il collector applica una seconda barriera eliminando anche query URL generiche, Authorization/Cookie/Set-Cookie e metadata DB sensibili prima di inviare dati ai backend;
- aggiunto un overlay Compose opzionale `docker/compose.observability.yml`: il deploy standard resta indipendente; attivando l'overlay partono OpenTelemetry Collector, Prometheus, Loki, Tempo e Grafana con versioni pinning e volumi persistenti;
- retention Prometheus/Loki/Tempo e trace sampling sono configurabili tramite environment; Grafana è esposto di default solo su loopback, disabilita l'accesso anonimo e richiede password amministrativa;
- Grafana riceve provisioning automatico dei datasource Prometheus, Loki e Tempo; un eventuale URL pubblico/autenticato può essere configurato per essere mostrato agli Administrator;
- `GET /api/admin/observability` richiede la policy `Administrator` e restituisce soltanto stato telemetria, presenza dell'exporter e URL dashboard normalizzato: endpoint OTLP, sampling e secret non vengono esposti;
- `/admin` mostra un pannello tecnico responsive con stato telemetria/exporter e link Grafana, interamente localizzato in italiano e inglese;
- la CI valida il merge Compose, avvia e verifica healthy la configurazione production del Collector, esegue test unit/API su enrichment/redazione/activity/metriche e realizza uno smoke reale exporter OTLP → Collector controllando che il servizio `vuxo-api` sia effettivamente ricevuto;
- Playwright copre pannello osservabilità, link Grafana, i18n IT/EN e layout mobile insieme al resto della dashboard amministrativa;
- la guida operativa completa è in `docs/operations/observability.md`.

## Docker runtime e persistenza

- l'API usa un Dockerfile multi-stage .NET 10: l'SDK resta confinato allo stage di build e l'immagine finale deriva dal solo runtime ASP.NET, esegue come utente non-root e include un healthcheck HTTP su `/health`;
- il Compose development avvia PostgreSQL e Redis con named volume, healthcheck, restart policy e porte host bindate esclusivamente a `127.0.0.1`; le porte locali sono configurabili per evitare collisioni;
- il Compose production richiede esplicitamente immagine API, password PostgreSQL e chiave JWT da environment/secrets e non contiene credenziali reali nel repository;
- PostgreSQL e Redis production non pubblicano alcuna porta host: sono raggiungibili soltanto sulla rete Docker; l'API espone `8080` nel container ma viene bindata sul server soltanto a `127.0.0.1:${VUXO_API_PORT:-8080}`;
- PostgreSQL e Redis hanno healthcheck reali; l'API aspetta entrambi healthy prima di partire e Redis usa AOF con `appendfsync everysec` per mantenere lo stato oltre il ciclo di vita del container;
- i named volume `vuxo-postgres`, `vuxo-redis` e `vuxo-ollama` sopravvivono ai normali recreate/deploy; `docker compose down -v` è documentato come operazione distruttiva da non usare in produzione;
- il profilo `edge` avvia `cloudflared` soltanto dopo l'healthcheck API; per il tunnel remotely managed la published application deve usare `http://api:8080` come Service URL, non `localhost`, perché API e tunnel sono container separati sulla stessa rete;
- aggiunto `scripts/test-docker-runtime.sh` come integration smoke canonico: valida Compose dev/prod/edge, builda l'immagine production, verifica l'assenza dell'SDK, avvia dev DB/cache, controlla health e isolamento porte production, prova la raggiungibilità di `api:8080` da un container sibling, scrive marker in PostgreSQL/Redis, ricrea i container e verifica che i marker sopravvivano;
- la CI esegue il runtime smoke in un job `docker-runtime` indipendente dai test .NET e Playwright, così regressioni IaC/persistenza bloccano il merge;
- aggiunta `docs/operations/docker-runtime.md` con avvio locale/production, Cloudflare route, named volume, recreate sicuro e combinazione con l'overlay osservabilità;
- questa feature non aggiunge nuove stringhe UI: le regole i18n IT/EN della 0.0.1 restano invariate e continuano a essere verificate dalla suite frontend/Playwright.

## Database e migration

- la migration iniziale EF Core hand-written espone metadata `DbContext` e `Migration` espliciti, così `Database.GetMigrations()` e `MigrateAsync()` possono indicizzarla anche senza il file `.Designer.cs` generato da EF;
- aggiunta `202609160002_WorldGeneration` per `world_definitions` e `world_chunks`, con metadata EF espliciti, chiave composta sui chunk e foreign key verso la definizione del mondo;
- aggiunta `202609160003_ExclusiveContent` per i grant personali, con `GrantEventId` univoco e indice su player/stato/scadenza;
- aggiunta `202609160004_AuditQueries` con indici su timestamp evento, tipo+timestamp e correlation ID; resta disponibile l'indice player+timestamp della migration iniziale;
- oltre al regression test offline sulla discovery, la CI avvia PostgreSQL 17 reale e ogni integration test crea un database isolato, vuoto, applica `Database.MigrateAsync()` e lo elimina a fine test;
- il gate verifica che tutte le migration arrivino allo schema corrente e che siano presenti le tabelle `player_characters`, `game_events`, `world_definitions`, `world_chunks` ed `exclusive_content_grants`;
- `PlayerCharacterRepository` è verificato end-to-end su Npgsql: persistono ID, owner, nome, livello, tutti e sei gli attributi, statistiche derivate e tutti i campi dell'aspetto; il database rifiuta realmente un secondo personaggio con lo stesso `OwnerId` tramite unique violation PostgreSQL `23505`;
- `GameEventStore` è verificato su PostgreSQL reale per append, lookup e query per player/intervallo UTC; il payload `jsonb` è confrontato semanticamente perché PostgreSQL normalizza ordine delle proprietà e whitespace senza alterare il contenuto JSON;
- la CI esegue anche un restore drill `pg_dump` → nuovo database → `pg_restore` e verifica il dato ripristinato;
- credenziali production restano esclusivamente in environment/secrets; anche i dummy secret dei test Docker vengono generati a runtime invece di essere versionati come literal;
- `docs/operations/postgresql.md` documenta migrazioni, gestione credenziali, backup, restore drill e procedura di restore production.

## Quality rules

- ogni nuova UI deve riusare MUI/design token, funzionare in tema chiaro/scuro e considerare layout mobile;
- ogni stringa user-facing deve passare da i18n con almeno italiano e inglese;
- ogni regola deterministica deve essere testata, preferibilmente con test parametrizzati;
- ogni bugfix deve avere un regression test quando tecnicamente possibile;
- ogni lavoro non banale deve essere collegato a una issue e riflesso nel development ledger;
- ogni feature/bug chiuso deve avere una risoluzione esplicita nella issue e ledger aggiornato;
- ogni nuova versione deve includere bump versione, metadata coerenti, patch note e test verdi.
